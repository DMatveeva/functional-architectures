Я работаю на проекте с микросервисами, стек Java + Spring Boot + Hibernate.
У во всех наших микросервисах используется Многоуровневая архитектура. 
И везде очень запутанный слой сервисов. Сервисы создают и изменяют объекты Entity - это классы ORM, которые маппятся на таблицы в БД.

Сейчас мы разрабатываем новый микросервис. И я предложила внедрить разделение запросов и команд CQRS. 
Теперь когда приходит GET-запрос с UI, мы не используем сущности Hibernate. Сервис вызывает метод репозитория, который загружает неизменяемый record с нужными данными из БД через native sql или jpql.
Это конечно не гексагональная архитектура, но получается, наши record'ы не зависят от слоя СУБД. А вот слой СУБД от них зависит. Т.е. при таком подходе, как мне кажется, соблюдается DIP.

Техлид одобрил подход, мы стали делать GET запросы в таком стиле. 
И я захотела попробовать также немного внедрить DDD, но тут все оказалось сложнее. 

У нас есть класс (ORM):

```java
@Entity
@Table("token")
class TokenEntity {
  //...
    StateEntity state;
}

@Entity
@Table("token_state")
class StateEntity {

    BigDecimal supply;
}
```
В любом сервисе, если надо поменять какое-то поле в TokenStateEntity, например, supply, всегда повторяется одна и та же логика:
```java
//service
TokenEntity token = tokenRepository.findById(id); // загружаем токен
StateEntity state = token.getState();
if(state == null) { //проверяем, что state существует, если нет - создаем
    state = StateEntity.builder()....build();
    token.setState(state);
}
state.setSupply(total); // обновляем поле
```


И я подумала - все изменения StateEntity инициируются через TokenEntity. И StateEntity не может существовать в отрыве от TokenEntity. 
Так может быть запретить изменять StateEntity через сеттеры и менять состояние только через методы TokenEntity.

```java
@Entity
@Table("token")
class TokenEntity {
    StateEntity state;

    public void updateSupply(BigDecimal value) {
        if (state == null) {
            state = StateEntity.builder()...build();
        }
        state.setSupply(value);
    }
}
```

А еще, каждое изменение инициируется какой-то задачей. 
Например, задачу на изменение supply имеет тип CHANGE_SUPPLY.
И можно сделать потомков TaskEntity, каждый из которых будет вызывать свой метод у TokenEntity.

```java

@Entity
@Table("task")
class ChangeSupplyTaskEnity extends TaskEnity { // TaskEnity имеет поле token типа TokenEntity
    public void changeSupply(BigDecimal value) {
        token.updateSupply(value);
        this.status = SUCCESSFUl;
    }
}
```
Но все равно слой домена здесь зависит от слоя СУБД. Они смешаны, т.к. ORM.
Но я подумала, может быть, если сейчас заложить в наши Entity поведение, может быть в будущем будет возможность сделать эти объекты просто доменными объектами, и убрать их зависимость от ORM.
